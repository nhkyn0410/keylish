## Mục tiêu

Admin (UI + API) **chỉ chạy local**; production (Render/Vercel) không còn surface admin công khai. Đồng thời gom admin thành **một slice code sạch** để hết "rối" (hiện admin bị trộn vào module công khai) và để sau này tách `apps/admin-api` chỉ là bước nhỏ.

Cách tiếp cận: **modular monolith + gate** (không tách service ngay — tránh trả "thuế microservice" khi chưa có nhu cầu scale admin; nút thắt scale thật của hệ thống là DB + API công khai, không phải admin).

## Kiến trúc đích

```
Public :  user-web (Vercel) → API (Render, KHÔNG admin) → Supabase
Admin  :  admin-web (localhost:3002) → API local (localhost:3000, pnpm dev:api) → Supabase
```

Cùng một codebase API chạy 2 runtime: bản Render phục vụ user công khai (đã tắt admin), bản local phục vụ admin. Cả hai trỏ chung Supabase.

## Runbook (sau khi triển khai)

Chạy admin cục bộ:

```bash
pnpm dev:api          # API local :3000 → Supabase (admin bật vì NODE_ENV != production)
pnpm dev:admin-web    # admin-web :3002 → gọi API local :3000
```

Đăng nhập admin tại `http://localhost:3002` bằng tài khoản đã seed (`admin.khanh`). Thêm admin mới: `pnpm --filter @keylish/api seed-admin <username> <password>`.

## Rủi ro & lưu ý

- Admin chỉ dùng được khi **bật stack local** — đúng nhu cầu "chỉ xem tài nguyên", không quản lý từ xa/điện thoại được nữa.
- Local API thao tác **thẳng vào Supabase prod** → xoá topic/word, disable user là thật.
- Mặc định an toàn: quên set cờ trên Render thì admin vẫn **tắt** (vì `NODE_ENV=production`).
- Hoàn nguyên dễ: set `ADMIN_API_ENABLED=true` trên Render là mở lại; refactor module revert qua git.

## Khi nào mới nên tách `apps/admin-api` riêng (trigger tương lai)

- Admin phình thành app lớn (nhiều nghiệp vụ, nhiều người dùng admin).
- Cần cô lập mạng/compliance (admin chỉ trong VPN, khác hạ tầng).
- Admin có workload nặng (báo cáo/aggregation lớn) cạnh tranh tài nguyên với API công khai.
- Cần nhịp deploy/đội ngũ tách biệt.
